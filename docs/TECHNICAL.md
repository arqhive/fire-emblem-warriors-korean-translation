# 기술 문서

파이어 엠블렘 무쌍(3DS 일본판)의 파일 구조와 한글 패치 방식을 정리했습니다.
값은 모두 리틀엔디언입니다.

## 아카이브: LINKDATA

게임 데이터는 romfs의 `LINKDATA.idx` + `LINKDATA.bin` 한 쌍에 들어 있습니다.
코에이 테크모 공용 형식이며 이 게임에서는 압축을 쓰지 않습니다.

- `.idx`는 8바이트 엔트리의 배열입니다. 앞 u32의 상위 바이트가 플래그, 하위 3바이트가 크기, 뒤 u32가 `.bin` 안의 오프셋입니다.
- 엔트리(슬롯) 안은 다시 중첩 컨테이너입니다. `u32 count` 뒤에 `{u32 offset, u32 size}`가 count개 이어지며, 첫 엔트리의 offset이 `4 + count*8`과 같은지로 컨테이너 여부를 판정합니다.
- 다국어 슬롯은 최상위 분기가 언어별로 나뉩니다. 11개 분기가 흔하며, 분기마다 가나 포함 비율을 재서 일본어 분기를 고릅니다. 중국어는 CP932로 읽으면 한자처럼 보이지만 가나가 없습니다.

구현: [`tools/linkdata.py`](../tools/linkdata.py), [`tools/extract_text.py`](../tools/extract_text.py).

## XL 텍스트 블록

메뉴·설명·전투 로그 등 대부분의 문자열이 들어 있는 블록입니다.

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0x00 | u32 | 매직 `0x134C58` |
| 0x04 | u32 | 하위 16비트만 총 크기와 일치합니다. 상위 16비트는 별개 값이라 크기 판정에 쓰지 않습니다. |
| 0x08 | u16 | 엔트리 수 |
| 0x0A | u16 | 엔트리 폭 |
| 0x0C | u32 | 표 시작 위치(`hdr`). 관측상 0x14 또는 0x1C. |

`hdr`부터 엔트리 배열이 있고, 그 뒤(`hdr + 엔트리수 × 폭`)부터 문자열 영역입니다.
문자열은 CP932 널 종료이며, 엔트리의 offset은 `hdr` 기준 상대값입니다.

엔트리 안에서 offset 필드의 개수와 위치는 폭마다 다릅니다.

| 폭 | 구성 |
|---|---|
| 4 | offset 1개 |
| 8 | id + offset |
| 18 | 메타 14바이트 + offset 1개 |
| 64 | offset 16개(캐릭터 이름의 표기 변형) |

그래서 위치를 가정하지 않고, 4바이트 정렬된 자리 중 **모든 행에서 문자열 영역을 가리키거나 비어 있는 열**을 offset 열로 판정합니다.
이렇게 하면 문자열을 가리키는 참조를 빠짐없이 알 수 있어 문자열 영역을 통째로 다시 깔 수 있습니다.
개별 문자열의 길이 제한이 사라지고 블록당 문자열 총량만 제약으로 남습니다.
블록 크기 자체는 그대로라 `.idx`나 상위 컨테이너를 건드리지 않습니다.

안전장치로, 표가 가리키지 않는 바이트가 문자열 영역에 남아 있으면(널 패딩 제외) 구조를 잘못 읽은 것으로 보고 그 블록은 수정하지 않습니다. UTF-16 문자열이 든 블록 11개가 여기에 걸려 보호됩니다.

구현: [`tools/xl.py`](../tools/xl.py).

## 순차 대사 레코드

XL 밖에 따로 있는, 길이 접두가 붙은 대사 레코드입니다. 두 가지 배치가 관측됩니다.

- `u16 순번, u16 길이`
- `u16 순번, u16 큐, u16 길이`

저장된 길이는 **CP932 바이트 수 + 줄바꿈 수 + 1**이고, 게임은 이 값으로 다음 레코드를 찾습니다. 실제 바이트 레코드는 널에서 끝납니다. 원본 일본어는 줄바꿈 말고 모두 2바이트라 「글자 수×2+1」과 같은 값이 되지만, 반각 문자가 섞인 번역문에 그 식을 쓰면 반각 하나마다 1씩 커져 둘째 대사부터 앞 대사가 반복되거나 빈칸이 나옵니다(v0.1의 결함). 한 장면만 원문·한글·두 가지 길이 식을 섞은 진단 빌드로 확인했습니다. 다른 언어(영어·프랑스어 등 8개)는 줄바꿈이 없는 1바이트 문자라 「바이트 수 + 1」로 적혀 있어 같은 규칙과 맞습니다.

길이가 바뀌면 자원 전체를 `LINKDATA.idx`를 통해 재배치하고, 레코드 ID와 큐, 형제 데이터를 그대로 보존합니다.

구현: [`tools/dialogue_records.py`](../tools/dialogue_records.py), [`tools/patch_dialogue.py`](../tools/patch_dialogue.py).

## UTF-16 훈장 자원

훈장 문구는 `2/<언어>/7` 블록에 UTF-16LE 로 들어 있습니다. 구조 자체는 보통의 XL 이고
문자열만 UTF-16 이라, 널 한 바이트로 끊어 읽던 예전 파서가 문장 중간에서 잘라 읽었을 뿐입니다.
`xl.parse(..., wide=True)` 로 종료를 짝수 경계의 널 두 바이트로 보면 그대로 재구성됩니다.
일본어 분기(`2/0/7`)만 바꾸고 다른 언어 블록은 손대지 않습니다. 88종 176참조를 반영했습니다.

구현: [`tools/apply_medals.py`](../tools/apply_medals.py).

## 제어코드

문자열 안에 ESC(0x1B) 제어코드가 섞여 있습니다. `A`, `P`, `F`는 인자 1바이트를 더 갖는 3바이트 코드이고 나머지는 2바이트입니다.

| 코드 | 뜻 |
|---|---|
| `\x1bT` 본문 `\x1bZ` `\x1bT` 읽기 `\x1bZ` | 후리가나. 한국어에는 필요 없어 본문만 남깁니다. |
| `\x1bP<n>` | 버튼 아이콘. 지우면 화면에서 아이콘이 사라집니다. |
| `\x1bA<n>` … `\x1bR`, `\x1bF<n>` | 색·글꼴 강조. |

번역문에서도 살려야 하므로 후리가나를 뺀 나머지는 `{A6}`, `{PY}`, `{R}` 같은 플레이스홀더로 보이게 하고, 바이트로 되돌릴 때 그대로 복원합니다. 원문에 중괄호를 쓰는 문자열은 없어 충돌하지 않습니다.

`%s`, `%1s` 같은 포맷 지정자는 개수와 종류를 그대로 유지해야 합니다. 빌드 시 제어코드와 포맷을 모두 대조합니다.

구현: [`tools/ctrl.py`](../tools/ctrl.py), 검사는 `tools/kopatch.py`의 `lint`.

## 폰트

본문 글꼴은 슬롯 22의 G1T 텍스처에 든 1024×1024 ETC1A4 글리프 아틀라스입니다. 8×8 타일을 4×4 서브블록 네 개(모턴 순서)로 나누고, 블록마다 알파 8바이트와 ETC1 색 8바이트를 씁니다. 알파 니블은 열 우선이고 Y축이 뒤집혀 있습니다. 한글은 알파 니블만 바꿔 그리므로 색 부분은 원본 그대로 남습니다.

글자 코드는 `code.bin` 안의 조회 표로 아틀라스 칸과 이어집니다. `code.bin`은 BLZ(역방향 LZ77)로 압축되어 있습니다.

일본어 글리프를 덮어쓰지 않기 위해, 작은 ARM 훅을 넣어 CP932 사용자 정의 영역 `F040`부터 `F9FC`까지를 비어 있는 아틀라스 칸 1926번부터 3805번에 매핑합니다. 기존 일본어 조회 표는 건드리지 않으며 한글 최대 1,880자를 넣을 수 있습니다.

구현: [`tools/ctrtex.py`](../tools/ctrtex.py), [`tools/hangul_font.py`](../tools/hangul_font.py), [`tools/blz.py`](../tools/blz.py).

## 그래픽

텍스처는 G1T 컨테이너에 들어 있습니다. 3DS 변형이라 0x08에 총 크기, 0x0C에 오프셋 표, 0x10에 텍스처 수, 0x14에 플랫폼(5 = 3DS)이 옵니다. 텍스처 헤더의 두 번째 바이트가 포맷, 세 번째가 가로세로 지수이며 데이터는 헤더 +20부터입니다.

쓰이는 포맷은 ETC1A4(1바이트/픽셀)와 ABGR32입니다. ABGR32는 RGBA가 완전히 일치하도록, ETC1A4는 알파 양자화와 보존 범위를 확인한 뒤 씁니다.

구현: [`tools/g1t.py`](../tools/g1t.py), [`tools/ctrtex_encode.py`](../tools/ctrtex_encode.py), 조사는 `tools/inventory_graphics.py`.

## HOME 메뉴

`exefs`의 배너(`banner.bin`)는 CBMD 컨테이너입니다. 헤더는 0x88바이트이고 0x08부터 u32 CGFX 오프셋 31개, 0x84에 CWAV 오프셋이 옵니다. CGFX는 LZ11로 압축되어 있습니다.

변종 0, 1, 9, 10에 글자가 있으며 9가 일본어, 0과 1과 10은 같은 영문 텍스처입니다. 모두 COMMON1 256×128 RGBA8(PICA format0)이고, **G1T와 달리 Y축을 뒤집지 않는 모턴 ABGR**입니다. 변종 0에는 공통 장면이 함께 들어 있어 텍스처 밖 바이트를 보존해야 합니다.

게임 이름은 `icon.bin`(SMDH)의 언어 슬롯에 있습니다. 언어 0/1/7의 short/long title과 publisher를 한국어로 바꾸고 나머지 언어·아이콘 그림·설정·지역 정보는 바이트 단위로 보존합니다.

[`tools/home_menu_assets.py`](../tools/home_menu_assets.py)가 LZ11 해제와 CBMD 읽기를,
[`tools/build_home_banner.py`](../tools/build_home_banner.py)가 LZ11 압축과 CBMD 재조립을 맡습니다.
텍스처 payload 만 바꾸고 장면·모델·애니메이션과 CWAV 오디오는 바이트를 보존하며, 압축한 뒤 되풀어
원본과 일치하는지 확인합니다. 한글 텍스처가 더 잘 압축돼 배너는 534,080 에서 516,288 바이트로 줄었습니다.

CWAV 는 32바이트 정렬 위치에 옵니다. 재조립할 때 31개 CGFX 오프셋과 `0x84` 의 CWAV 오프셋을
다시 계산해 넣습니다.

## 패치 방식

산출물은 **CIA 재빌드**입니다. romfs 안의 `LINKDATA`와 ExeFS의 `.code`·배너·아이콘을 갈아 끼운 CIA를 만들어 설치합니다.

### LayeredFS 를 쓸 수 없는 이유

Luma3DS 의 게임 패치(LayeredFS)로 이 게임의 romfs 를 덮으면 **타이틀 화면에서 반드시 죽습니다.**

#### 확인된 사실

| 조건 | 결과 |
|---|---|
| LayeredFS 끔 | 정상 |
| **추출한 원본 `LINKDATA` 를 LayeredFS 로 배치** | **크래시** |
| 패치본을 LayeredFS 로 배치(본편만 / 업데이트만 / 둘 다) | 크래시 |
| CIA 의 romfs 를 직접 교체 | 정상 |

원본을 그대로 얹어도 죽었으므로 **패치 내용과는 무관합니다.** romfs 를 어디서 읽느냐만으로 갈립니다.

크래시는 완전히 결정론적입니다. 여러 번의 덤프에서 `pc=0x60000010`(존재하지 않는 주소), 레지스터,
코드 덤프가 바이트 단위로 같았고, 항상 타이틀 화면의 `title_pressbutton_update_in.bflan` 을
처리하던 중이었습니다. 타이밍이나 읽기 속도 문제가 아닙니다.

처음에는 에뮬레이터(Azahar)에서 같은 파일이 정상 동작해 실기만의 문제처럼 보였습니다. 그러나 그것은
업데이트 없이 CXI 를 직접 부팅한 경우였고, 실기와 같은 조건을 만들면 Azahar 도 똑같이 죽습니다(아래).
**에뮬 결과로 실기 동작을 판단할 때는 설치 상태까지 같게 맞춰야 합니다.**

#### 원인 — 에뮬레이터로 확정

LayeredFS 는 **실행 중인 타이틀(본편) TID 폴더의 romfs 를 본편과 업데이트 두 아카이브에 모두 적용합니다.**
그런데 이 게임은 두 아카이브에 **같은 경로 `/LINKDATA.bin` 으로 서로 다른 파일**을 둡니다.

| 마운트 | 파일 | 크기 | 슬롯 수 |
|---|---|---|---|
| 본편 | `/LINKDATA.bin` | 1,392,747,100 | 13,070 |
| 업데이트 | `/LINKDATA.bin` | 111,236,698 | 14,301 |

본편 폴더에 넣은 1.4GB 파일이 업데이트 자리에도 들어가므로, 게임이 업데이트 아카이브를 읽을 때
본편용 인덱스와 데이터를 받게 됩니다. 슬롯 구성이 맞지 않으니 잘못된 값을 함수 포인터로 삼아
존재하지 않는 주소로 뜁니다. 폴더 하나로 서로 다른 두 파일을 동시에 표현할 수 없으므로
**원리적으로 LayeredFS 로는 해결할 수 없습니다.**

Azahar 로 실기와 같은 조건을 만들어 확인했습니다. 원본 CIA 를 복호화만 해서 설치하고
(업데이트·DLC 포함), 패치는 mods 폴더로만 얹었습니다.

1. 실기와 같은 배치에서 **Azahar 도 타이틀 화면에서 죽었습니다**(정의되지 않은 명령, `pc=0x00000000`).
2. 로그에 `LayeredFS replacement file in use for /LINKDATA.bin` 이 **두 번** 찍혔습니다.
3. 업데이트 TID 폴더(`0004000E0F70C100`)를 **없애도 여전히 두 번** 찍혔습니다.
   본편 폴더 하나가 두 아카이브를 모두 덮는다는 뜻입니다.

이 원인으로 관찰이 모두 설명됩니다.

- **원본을 얹어도 죽은 이유**: 본편 원본 1.4GB 가 업데이트 자리에도 들어갑니다. 내용이 원본이어도
  *어느 아카이브의 파일이냐* 가 틀리면 깨집니다.
- **업데이트 폴더를 꺼도 죽은 이유**: 본편 폴더가 여전히 양쪽을 덮습니다.
- **업데이트 없이 부팅하면 정상인 이유**: 업데이트 아카이브가 없으니 본편에만 적용됩니다.
  초기에 Azahar 로 CXI 를 직접 부팅해 확인한 것이 이 경우라, 에뮬에서는 되는 것처럼 보였습니다.
- **CIA 는 정상인 이유**: 각 아카이브가 자기 파일을 제대로 갖습니다.

에버 오아시스는 같은 3DS·같은 Luma 로 LayeredFS 가 잘 됩니다. 본편과 업데이트에 같은 이름의
서로 다른 파일을 두지 않기 때문입니다.

### 무엇을 바꾸는가

| 위치 | 파일 | 내용 |
|---|---|---|
| romfs | `LINKDATA.bin` | 텍스트, 순차 대사, 그래픽, 훈장, 한글 폰트 글리프 |
| romfs | `LINKDATA.idx` | 대사 재배치로 옮긴 자원의 위치표 |
| ExeFS | `.code` | 한글 코드 매핑 ARM 훅 88바이트 |
| ExeFS | `banner`, `icon` | HOME 배너와 게임 이름 |

romfs 에서는 이 두 파일이 전부이고 `movie`·`sound`·`voice` 는 손대지 않습니다.

### 코드 훅을 CIA 에 넣는 법

`.code` 는 BLZ 로 압축돼 있고 훅은 압축을 푼 코드 기준입니다. 그래서 압축을 푼 뒤 패치하고,
exheader(SCI) `0x0D` 의 bit0(`CompressExefsCode`)을 꺼서 그대로 넣습니다. 크기가
2,901,464 에서 4,870,144 바이트로 늘지만 문제되지 않습니다.

훅이 들어가는 cave(본편 `0x444CF0`)는 text 섹션의 페이지 패딩 영역입니다. exheader 의
text size(4,476,144)보다 뒤지만 페이지 수(1093 = 4,476,928바이트)에는 들어가며, 실기에서
동작을 확인했습니다.

### CIA 를 다시 싸는 순서

1. pyctr 로 콘텐츠를 복호화합니다(본편은 seed 암호화라 `seeddb.bin` 이 필요합니다).
2. 3dstool 로 CXI 를 분해합니다(`--header --exh --logo --plain --exefs --romfs`).
3. romfs 와 ExeFS 를 갈아 끼웁니다.
4. `--not-encrypt` 로 다시 쌉니다. 이 옵션을 빠뜨리면 원본 헤더의 '암호화됨' 플래그가 남아
   본체가 평문을 복호화하려 들고 데이터가 깨집니다(DLC 에서 실제로 겪었습니다).
5. makerom `-ignoresign` 으로 CIA 를 묶고, TMD 버전을 원본 값으로 되돌립니다
   (makerom 은 exheader 의 remaster version 을 쓰기 때문입니다).

DLC(`0004008C0F70C100`)는 콘텐츠가 6개인 CFA 묶음이고, 순차 대사가 든 것은 content 2·3·4 입니다.
인덱스 플래그가 콘텐츠를 구분합니다 — 본편 0, 업데이트 1, DLC c2·c3·c4 는 3·4·5 입니다.

### 배포

패치본 CIA 자체는 게임 데이터라 배포할 수 없습니다. romfs 단위 xdelta 차분과 코드 IPS 만
배포하고 사용자가 자기 원본으로 CIA 를 만듭니다. romfs 단위로 뜨면 `movie`·`sound`·`voice`
2.2GB 가 그대로 재사용돼 차분이 작고, 사용자 쪽에서 romfs 를 풀었다 다시 쌀 필요도 없습니다.

패처([`tools/fewpatch.py`](../tools/fewpatch.py), 배포본에서는 `patcher/lib/fewpatch.py`)는 CIA 의 TMD 에서 타이틀 ID 를 읽어 본편·업데이트·DLC 를
가르고 위 순서를 그대로 밟습니다. 단계마다 `manifest.json` 의 SHA-256 으로 검사합니다.

| 단계 | 검사 |
|---|---|
| romfs 를 꺼낸 뒤 | 원본 romfs 의 크기·SHA-256. 다르면 다른 버전이거나 이미 패치한 파일로 보고 멈춥니다. |
| xdelta 적용 뒤 | 결과 romfs 의 SHA-256. |
| `.code` BLZ 해제 뒤·IPS 적용 뒤 | 원본·결과 `.code` 의 SHA-256. |
| 배너·아이콘 | payload 파일 자체의 SHA-256. |

콘텐츠가 모두 평문(CIA 암호 없음, NCCH NoCrypto)이면 키 없이 그대로 복사하고, 아니면 pyctr 로
복호화합니다. 외부 도구는 작업 폴더를 cwd 로 두고 짧은 영문 이름만 넘깁니다(한글·일본어 경로 대책).
원본 CIA 세 개로 돌린 결과는 빌드 도구로 만든 한글판과 콘텐츠 11개의 SHA-256 이 모두 같습니다.
파일 전체로는 티켓 274바이트만 다른데, makerom 이 매번 무작위 타이틀 키를 넣기 때문입니다.
본편 기준 임시 공간은 4.5GB 남짓, 실행 시간은 1분 안팎입니다.

같은 자원에 텍스트와 그래픽이 함께 들어 있는 경우가 있습니다(예: `base 6410` 은 제작사 로고와
주의 안내, `base 6421` 은 타이틀 로고와 하단 저작권). 자원 하나에 모든 변경을 모아 반영해야 하며,
텍스트 재구성으로 절대 오프셋이 움직이므로 원본 절대 위치를 새 아카이브에 그대로 쓰지 않습니다.
